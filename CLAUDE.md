# Правила проекта

## Разметка литеров на генпланах (рамки подъездов)
- Рамка подъезда — прямоугольник с ПРЯМЫМИ углами в пиксельном пространстве (учитывать аспект изображения: перпендикуляр считать в px, не в %).
- Верхнее ребро — вдоль внешней кромки крыши (кроны деревьев могут её перекрывать — продлевать линию по чистому участку).
- Куб = светлая крыша + тёмное тело; высота рамки покрывает оба. Крыша основных литеров — всегда четырёхугольник.
- Межподъездный шов виден только на крыше — вниз через тело его продолжать мысленно.
- Соседние подъезды одного литера ДЕЛЯТ общее ребро по шву: правый край рамки одного = левый край рамки другого (одинаковые координаты, одна ось наклона на весь литер).
- Зелёные круги-геометки и соседние строения (1А, 1Б, 1В…) игнорировать — они наползают на литеры.
- Цвет рамок: #a3312b, stroke-width 2 (как в ЖК «Рекорд»).
- Пиксельные сканы кромок ненадёжны (штриховка парковок, текст, деревья): проверять примеркой — оверлей рамки на кропе, глазами.

## Заливка помещений на поэтажных планах
- Контур всегда прорисовывать детально по стенам: накладывать на план сетку 5 % (2× масштаб), снимать координаты каждой стены, вырезать лестницы и чужие помещения выступами/вырезами, дуги — 10–15 точками.
- Обязательная примерка: оверлей полигона на плане, глазами; затем сверка суммы включённых помещений с площадью по договору/КП.
- Служебные картинки примерки складывать в `build/` и удалять после.
- **Замена подложки плана** (эталон — ТЦ Самолёт, 1 этаж, `tc819_floor1_v3.png`): новая картинка → сетка 5 % (2×) → заново снять ВСЕ контуры этажа (проданные, арендаторы, МОП) по стенам нового скана, дуги фасада — 8–10 точками, лестницы вырезать → `ratio` = ширина/высота новой картинки → примерка оверлеем всех полигонов разом → удалить служебные файлы. Старые координаты не переносить — у нового скана другая обрезка.

## Карточки помещений на генпланах
Три шаблона, одинаковые во всех ЖК:
1. **Проданные** — тёмная карточка (фон #1b1916, текст #f2ede4, приглушённый #a9a196), перечёркнута крест-накрест (#e0938d), компактные отступы. Набор данных: номер и площадь, чип «Продано», номера БТИ, наименование актуальной т.т., категория актуальной т.т., данные сделки (дата продажи, факт. стоимость, выплата агенту, покупатель, годовой прирост). Кадастрового номера, рынка, аренды, управления, CAPEX/OPEX и эффективности в проданной карточке НЕТ.
2. **НТО, остановки, ЗУ** — свой сокращённый набор: место, площадь, статус, арендатор и ставка; поэтажного плана и БТИ нет.
3. **Обычные** (все остальные) — полная карточка: БТИ и кадастровый номер, рыночная цена, владелец, договор аренды (т.т., ставка, периоды, активация, каникулы, индексация, товарооборот), бывшие арендаторы, управление и платежи, CAPEX, OPEX, эффективность.

Эталон разметки — ЖК «Самолёт 3»; правки шаблона распространять на все шесть генпланов.

Порядок вывода карточек в панели подъезда зафиксирован: **в аренде → в простое → не введено в эксплуатацию → продано** (единая функция `unitRank`, внутри статуса — исходный порядок из выгрузки КП). Исключение — НТО: строго по номерам помещений (`keepOrder: true` у помещений из `nto_sz.js`).

## Архитектура генпланов (после рефакторинга 09.09.2026)
- Вся общая логика — в `genplan_core.js` (`window.GenplanCore(DCLogic)` → базовый класс). Расчёты, сводка, карточки правятся ТАМ один раз.
- В файле очереди `class Component extends window.GenplanCore(DCLogic)` — только данные очереди (полигоны, названия, поэтажные планы, численность) и осознанные отличия (свои `renderVals`, `unitFields`, `componentDidMount`; у С3 — `cxTotalOf`, у С345 — `summaryExtra`).
- `jk_logic.js` для матрицы ГЕНЕРИРУЕТСЯ из классов очередей (обёртка `window.OMJKLogic[N] = (DCLogic) => class extends GenplanCore(DCLogic) {…}`); после правки генпланов пересобирать.
- Регрессия: `build/Стенд рефакторинга.dc.html` сравнивает сводки/карточки/renderVals всех очередей с эталоном в localStorage — прогонять после правок ядра.
- **Локальные переопределения ядра.** У С1 и С3 (и у их копий в `jk_logic.js`) собственная `regRow`; при добавлении поля карточки арендатора править ЧЕТЫРЕ места: `genplan_core.js` → `regRow`, С1 → `regRow`, С3 → `regRow`, `jk_logic.js` → обе `regRow`. Перед правкой ядра — `grep '^  <метод>('` по проекту: всё, что перекрыто в очереди, править и там. Новую строку в шаблон карточки добавлять во все шесть генпланов (обычная и тёмная карточки — по два вхождения на файл).
- Строка «ФИАС» (после «Номера БТИ», во всех шести генпланах): ядро `fiasOf` — изменённый номер из `kp_addr.js` (`fias`) → «помещение N · номер изменён»; у «Магнит»/«Пятёрочка» (по `brand` в `tenantsReg`) строка есть всегда, без изменения → «помещение <БТИ> · совпадает с БТИ».
- Даты окончания договоров: поле `till` в записи реестра `tenantsReg`; ядро `regTillOf(r)` выводит только явное значение, без вычисления из периодов ставок.
- `costs_zpif.js` (`window.OMCosts`) — затраты на содержание из «Затраты на помещения_общий ЗПИФ.xlsx», ключ — кадастровый номер, привязка через `comp.cadastre[id|номер]`. В карточке подставляется, когда у помещения нет своего значения: «Плата УК» (УК), электричество/вода (вместо УПД РСО, если есть), «Налоги» (налог на имущество 1–2 кв.), «АХР управления» (только оценка; НПК — в «Управление»); взносы на капремонт МКД — строка «Капитальный ремонт» в OPEX. Ядро: `cxUnit/cxTaxesOf/cxAdminOf/costStr`, `opUnit/opRepairOf`.
- Общие реестры с ключом ЖК: `prices_net.js` (цены нетто), `rent_price.js` (прайс аренды бульвара), `sales.js` (сделки), `unit_status.js`, `utilities.js`, `volumes.js`.

## НТО (павильоны)
- Геометрия — `nto_pads.js`: площадки в % мастер-плана `assets/master_genplan.jpg`, пересчёт на подложки очередей через `OMGeo.master.boxes`; ключ площадки — номер со схемы (4/1, 1.1/2, 24.3/1…). Схема НТО (PDF) совмещается с мастером по картинке: полная ширина, вертикальный кроп y 6,25 %→96,7 %.
- Данные — `nto_sz.js` (СЗ на перевод НТО на ЛФ «КМ»): 13 павильонов, ключ `nto<N>` по номеру СЗ, помещения = площадки; `OMNtoSZ.apply(comp, jk)` в `componentDidMount` очереди ПОСЛЕ `this.tenantsReg = d.tenantsReg` (иначе договоры НТО затираются). С1 — НТО 5–8, С2 — 9–13, С6 — 1–4.
- Договоры аренды НТО — объект `TENANTS[<N>]` в `nto_sz.js` (одна запись или МАССИВ записей, если у помещений павильона разные арендаторы; поля как в `tenantsReg`: brand, tenant, activity, dogDate, contract=активация, till, holiday, rates, indexation, indexDate, mgmt, rateSqm, areaNote); запись тиражируется на все помещения павильона (`units`). Из ТЗ: дата договора и активация приходят от пользователя, ТЗ даёт ставку, каникулы, срок, индексацию, УК.
- **Планы павильонов** — `PLANS[<N>]` в `nto_sz.js` (`img`, `ratio`, `rooms[]` — контуры помещений в % картинки по внутренним граням стен, порядок = порядок `units`); типовой двухкомнатный — `PLAN_2ROOM` (`assets/nto_plan_2room.png`, пом. 1+2 слева / 3+4 справа от перегородки). `apply` собирает `c.ntoFloors[key]` в формате `tcFloors`; в селекторе этажей очереди — ветка `this.ntoFloors[id]` (С1 — в `floorsCfg`, С2 — в `bCfg` как `{addr, floors}`; С6 — так же через `bCfg`). Новый план: сохранить картинку в `assets/`, снять контуры по сетке 5 %, примерить оверлеем, добавить в `PLANS`.
- **Активация = дата акта приёма-передачи или акта доступа** (поле `contract` в реестре). Помещение с активацией — «В аренде», даже если арендные каникулы ещё идут; «В простое с арендатором» — только договор без акта.
- **Принцип «на помещение»:** договор заключается на павильон целиком, но в карточке каждого помещения все суммы пересчитываются по ЕГО площади: аренда в месяц = `rateSqm × площадь`, обеспечительный платёж = 1 месяц аренды помещения, плата НПК = 200 ₽/м² × площадь. Плейсхолдер `{mo}` в `rates[].rate` и `holiday` заменяется суммой в месяц; в `areaNote` — итог по павильону целиком (площадь, аренда, обеспечительный). Рыночная цена НТО — `marketPrice: 'нет данных'` до отдельных данных от пользователя.
- Карточка НТО — с 18.09.2026 ПОЛНАЯ форма как у литеров (рынок, договор, управление, CAPEX/OPEX, эффективность), плюс строки «Стоимость по ДКП» (10 000 ₽/м²) и «Правообладатель — Личный фонд «КМ»»; строка «Номер помещения» вместо БТИ, кадастр — ЗУ. Лишние поля убираются точечно по запросу. Флаги `isNto`/`fixedStatus` в данных не ставить (они включают сокращённый шаблон).
- **На плане:** красные площадки с подписями номеров площадок (4/1, 4/2…), клик — открывает панель павильона; при наведении на любую площадку над всем павильоном подсказка «НТО №N». Одну общую подпись вместо номеров площадок НЕ делать (отклонено).

## Данные
- **Из каждого ТЗ ВСЕГДА считывать строку «Управляющая компания» (НПК, ставка ₽/м²) и сразу вносить `mgmtCo`/`mgmtRate` (ставка + сумма в месяц по площади)/`mgmtActive` (с даты активации), не дожидаясь отдельной просьбы.**
- **Из каждого ТЗ ВСЕГДА вносить кадастровый номер** (`this.cadastre['<подъезд>|<номер>']` в `componentDidMount` очереди) **и мощность** (`powerKw` + `powerTz: true` на помещении в `units`, и `powerKw` в `tenantsReg`); после ввода проверить обе строки в открытой карточке.
- Кадастровый № у остановок и НТО — только номер ЗУ в формате «ЗУ 23:43:…», без пояснений в скобках.
- В поле «Арендатор» — только текущий арендатор (без пометок об уступке); прежний — в «Бывшие арендаторы» (`pastTenants`).
- **Внёс — открыл — проверил.** После каждого ввода данных открыть карточку в превью и глазами сверить каждую внесённую строку (НПК, ставки, даты, суммы с начала года). Управление карточка читает с ПОМЕЩЕНИЯ (`units`: `mgmtCo`/`mgmtRate`/`mgmtActive`), не из `tenantsReg` — ставить туда.
- **НПК — только в «Управление и платежи», в CAPEX НИКОГДА.** При вводе данных всегда ставить `mgmtCo`/`mgmtRate`/`mgmtActive` на помещении и проверять, что плата за управление и аренда с начала года посчитались. В «АХР управления» (CAPEX) — только оценка.
- **Плата за управление и аренду с начала года** в карточке считаются автоматически (`mgmtAccrued`/`rentAccrued`, 01.01.2026 → отчётная дата, по дням от активации/ставок), если в данных нет явных `mgmtPaid`/`rentPaid`. При вводе договора всегда заполнять ставки с датами и управление (`mgmtCo`, `mgmtRate` с суммой в месяц, `mgmtActive`), чтобы суммы считались.
- **Товарооборот в карточке** (`u.turnover`, ключи 1–12): для арендаторов с процентом от оборота цифры = годы договора — по цифре N показывается ставка N-го года (напр. «Вкусно и точка», ТЦ Самолёт: 1 → 3,7 %, 2–12 → 4 %). Помесячные суммы ставить только при наличии отчётов. **Всегда** при вводе ТЗ/договора/ДС проверять условие о проценте от оборота/выручки и сразу заполнять `u.turnover` по годам договора (от активации), не дожидаясь отдельной просьбы.
- Коммунальные услуги (utilities.js, по УПД РСО): в подстроках — фактические начисления; в итоге «Коммунальные услуги» — только периоды без действующего договора аренды (при арендаторе затраты возмещаемые и в итог не идут; расчёт по дням через `rentSegs`).
- **Плата УК (УК «Заполярье» и др., costs_zpif.js) арендатор ВСЕГДА возмещает** — при действующем договоре в итог CAPEX не идёт; показывается подстрокой в «Коммунальные услуги», в итоге — только дни простоя.
- «Аренда» в выгрузке КП по всем ЖК = помещение доступно для аренды, но простаивает.
- Личные фонды (ЛИЧНЫЙ ФОНД…, Морозов Д. С., ПРОФИТ КАПИТАЛ) — владельцы в составе ДВК, не арендаторы; «в составе ДВК» в подписи не писать.
- Названия: ЖК «Самолёт 1» (не «I очередь»).
